3. Bottleneck one — the LCP image is told to wait its turn

Lighthouse identifies the LCP element as div.card-image > a > picture > img, the lead story photo. Its markup, taken verbatim from the served HTML:

<img loading="lazy" decoding="async" width="580" height="435" src="…/big_580_435/public/2026-07/Pradhan.jpg">

The largest, most important image on the page carries loading="lazy". That instruction tells the browser it is safe to defer — so it is queued behind everything else already in flight, including 18 MB of advertising GIFs. The phase breakdown shows exactly that:

LCP phaseDurationShareWhat it means
TTFB2,595 ms11%Server took 2.6 s to return the HTML
Load delay17,011 ms72%The image sat in a queue, not downloading
Load time3,666 ms15%Actual download once it started
Render delay466 ms2%Paint after bytes arrived

Confirming it site-wide, the served homepage HTML contains:

  • 65 images with loading="lazy"
  • 0 with loading="eager"
  • 0 with fetchpriority="high"
  • 0 <link rel="preload"> hints of any kind

This is a blanket lazy-loading rule applied by the Drupal theme without excluding above-the-fold content. It is the single highest-leverage defect on the page: 72% of a 23.7-second metric caused by one attribute.

These three files are 86% of the entire page weight. Lighthouse's own efficient-animated-content audit estimates 17,960 KB of savings, and image-delivery-insight estimates 18,567 KB. The 40 KB figure above is not an estimate: we downloaded bmw.gif and re-encoded it with ffmpeg (H.264, CRF 30) — the file in this demo's "after" page is that exact 40,175-byte result.

GIF is a 1987 format with no interframe video compression. Animated advertising creative in GIF form is the most expensive possible way to ship motion, and the fix does not require touching the ad-serving relationship — only the creative file format.

Notice that three of these — GTM (which itself injects three separate gtag/js containers, 161 + 163 + 151 KB), the ad manager, and the Facebook pixel — account for 3,592 ms of the 3,890 ms. Supporting audits: bootup-time 6.9 s of script evaluation, mainthread-work-breakdown 10.5 s, unused-javascript 542 KB shipped and never executed. Blocking time is what makes a page feel "broken" rather than merely slow: taps register but nothing happens.

6. Bottleneck four — 74 render-blocking stylesheets

The served HTML contains 74 <link rel="stylesheet"> tags and 54 <script> tags. The stylesheets total only 121 KB — the cost is not bytes, it is 74 serialised round-trips that must all complete before the browser paints a single pixel. Lighthouse's render-blocking-insight puts the recoverable time at 8,670 ms.

Worse, the list includes Drupal administrative CSS being served to anonymous readers who can never see an admin screen: claro/css/components/system-admin--admin-list.css, system-admin--modules.css, ui-dialog.css, action-link.css and others. This is an unaggregated Drupal install — turning on CSS/JS aggregation in Drupal's performance settings collapses most of these into a handful of files with no code change at all.

7. Bottleneck five — slow origin and weak caching

  • TTFB 2,560 ms. document-latency-insight estimates 2,460 ms recoverable. An uncached Drupal render on every request; a full-page cache or CDN edge cache fixes it.
  • 22 resources with short cache lifetimes, ~790 KB re-downloaded on repeat visits (uses-long-cache-ttl). Painful for a news site whose readers return daily.
  • No preconnect hints for the ad, font and analytics origins — 340 ms of avoidable DNS/TLS handshakes.

8. Secondary findings

  • Article thumbnails served as PNG where JPEG/AVIF belongs — the lead story image is a 434 KB PNG of a photograph. modern-image-formats: 618 KB savings; uses-optimized-images: 74 KB.
  • offscreen-images: 145 KB of images loaded but never seen.
  • DOM of 1,984 elements.
  • 6 KB unminified JS, 13 KB legacy polyfills.

9. Causal chain, in one sentence

A slow uncached origin (2.6 s) hands the browser an unaggregated document with 74 blocking stylesheets (delaying first paint to 11.1 s); the browser then races 18.3 MB of GIF advertising against a lead photo that has been explicitly marked deferrable, so the photo waits 17 s in a queue (LCP 23.7 s); meanwhile 2 MB of ad and tag scripts occupy the main thread for 3.9 s, so the page does not respond to touch until 34.4 s.

10. Reproducing this audit

npx lighthouse https://www.thedailystar.net/ --form-factor=mobile --screenEmulation.mobile --throttling-method=simulate --only-categories=performance --output=json

Markup claims verified against the served HTML: curl -sL https://www.thedailystar.net/ | grep -c 'rel="stylesheet"' → 74, and grep -c 'loading="lazy"' → 65, grep -c 'fetchpriority' → 0. Figures reflect the homepage as served on 25 July 2026 and will drift as the front page changes.
